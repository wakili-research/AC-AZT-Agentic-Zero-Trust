## What the simulation is
A deterministic policy simulation of the AC-AZT gateway, run on 240 constructed cases. The cases are 60 base actions (30 cloud, 15 edge, 15 IoT), each run under four conditions: benign, injection, scope escalation and unsafe context.

What it implements:
- the mandatory rules;
- the risk score R = Σ w·{I, P, U, D, S};
- autonomy ceilings A2, A3 and A4 only;
- a postcondition check.

What it does **not** implement:
- cryptographic capabilities;
- domain adapters;
- an approval workflow;
- trusted computation of input attributes.

Scope validity, interface type, freshness and rollback availability are Boolean fields supplied with each case, and the gateway trusts them. "Risk-adaptive" means context-sensitive, action-level authorization with a fixed threshold. There is no learning and no online adaptation.

## Oracle
The oracle labels each case PERMIT, APPROVAL_REQUIRED or DENY (33 / 32 / 175). The authors wrote the benign labels by hand for each base action. Variant labels follow six documented properties. The oracle is **method-separated**: it is computed without calling any method. It is **not independent**: the labellers were not blinded, there were no external annotators, and the variant properties coincide with AC-AZT's mandatory rules. Each attack variant sets exactly the flag that one mandatory rule checks.

## Metrics (same definitions and denominators as the paper)
**Terminology:** the paper renamed the notebook's `LASR` to **OPER** (Oracle-PERMIT Execution Rate), because it counts execution, not success. ## Statistical status
Results are **descriptive counts on a purposively constructed suite**. The four variants of each base action are correlated. The case-level Wilson intervals and exact McNemar tests in the original output are **exploratory**, are kept for the record, and are not used for inference. 0/170 is a result on this suite, not an estimate of a real-world attack rate.

## Known limitations shown by the package
- **Approval bypass.** 3/32 approval-required cases executed. Their need for approval is not encoded in any rule, and their risk is below T = 0.45.
- **Trusted-attribute probe** (post hoc, gateway unchanged, see `results/v3_trusted_attribute_probe_*.csv`). When the violation was present in the raw attributes but the flag was left True, the gateway executed 28/60 scope-escalation probes and 29/60 injection probes (31/60 each without the risk increase). For comparison, it executed 0/120 of the benchmark's flagged variants.
- **Rollback** is recorded as successful whenever `rollback_available=True`. It is a Boolean condition, not a compensation workflow that could fail.
- **Invariant checks** reuse the gateway's input flags, so zero violations means internal consistency, not independent verification.
- **Threshold.** T = 0.45 is the configured default for the reported evaluation; the available package does not establish external preregistration or that no developmental exploration informed this setting. On this suite, T = 0.35 would have had a more favorable observed execution-rate trade-off.


## Important interpretation of the post-hoc probe
The **scope mismatch** probe demonstrates that the current gateway trusts a supplied scope-validity Boolean rather than checking requested target counts against approved scope. The **appended-text** probe shows that adding instruction text does not by itself change structured policy authorization when the flag remains permissive. Neither probe measures a deployed LLM agent following malicious instructions; no agent reads that text. Probe oracle labels were defined by the authors using the benchmark's safety criteria, not independent blinded annotators.

## Disclosure
This package is a controlled, constructed, author-labeled simulator benchmark. It does not demonstrate safety or robustness of a deployed agent, resistance to adaptive prompt injection, cryptographic capability enforcement, approval workflow operations, or stateful compensation under partial failures.
